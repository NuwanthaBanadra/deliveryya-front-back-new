# Deliveryya Backend API Documentation

## 1) Overview

This document was generated by reading the backend controllers, DTOs, security configuration, and validation annotations in the Deliveryya backend source code.

- **Base URL:** `http://localhost:8080/api/v1`
- **Content Type:** `application/json` unless noted otherwise
- **Primary response wrapper:** `ResponseDto<T>`
- **Authentication:** JWT-based security with stateless sessions
- **Response style:** Most endpoints return an HTTP status plus a `ResponseDto` payload containing `status`, `message`, `desc`, `exData`, and/or `object`

> Note: Some controller methods return `SseEmitter` instead of `ResponseDto` for server-sent events.

---

## 2) Security & Access Rules

### 2.1 Public routes configured in `SecurityConfig.PUBLIC_PATTERNS`
These routes are intended to be reachable without authentication:

- `POST /api/v1/users/sign-up`
- `POST /api/v1/users/login`
- `GET /api/v1/email/verify-email-by-token`
- `GET /api/v1/live-locations/subscribe/**`
- `GET /api/v1/access/get-access-details`
- `POST /api/v1/users/send-reset-password-email` *(configured as public pattern in code)*
- `POST /api/v1/users/reset-password-email` *(configured as public pattern in code)*

### 2.2 Authenticated routes
All other endpoints require a valid JWT unless the service layer performs a separate check.

### 2.3 Method-level role restrictions
A few endpoints use `@PreAuthorize`, including:

- `POST /api/v1/payment/get-payment-records`
- `POST /api/v1/access/grant-access-to-user-role`
- `POST /api/v1/access/grant-access-to-user`
- `POST /api/v1/orders/request-codes`

### 2.4 JWT header behavior
The JWT filter can emit a refreshed token in the `x-token` response header for valid requests when token renewal conditions are met.

---

## 3) Standard Response Envelope

Most endpoints return a response similar to:

```json
{
  "status": 200,
  "message": "Success",
  "desc": "Human readable description",
  "exData": {},
  "object": {}
}
```

### ResponseDto fields
- `status`: HTTP status code when explicitly set
- `message`: usually `Success` or `Error`
- `desc`: user-readable message
- `exData`: map of validation/business errors
- `object`: payload returned by the endpoint

### Error handling
The backend uses a global exception handler for validation and business errors.

- **400 Bad Request**: validation failures
- **409 Conflict**: business rule violations
- **401 Unauthorized**: missing/invalid JWT
- **500 Internal Server Error**: unhandled exceptions

### 4.1.3 Common user rules

- `dob`: past or present date
- `nic`: `\d{9}[VvXx]` or `\d{12}`

- `password`: 8–64 characters, must include uppercase, lowercase, digit, and special character
- `profileImg`: max 150 characters
- `gender`: required for update flows
- `verificationStatus`: optional in DTO, but used by service workflows

### 4.13.1 Role restriction for payment records
`POST /get-payment-records` allows these roles:
- `SUPER_ADMIN`
- `ADMIN`
- `OWNER`
- `MANAGER`
- `CLIENT`
- `MARKET_OWNER`
- `SECRETORY`
- `ACCOUNTS_MANAGER`
- `ACCOUNT_ASSISTANT`
- `MARKETS_MANAGER`

### 4.13.2 Payment record rules
- At least one of the following must be present: `orderCode`, `urgentJobCode`, `orderId`, `urgentJobId`, or `referencesCodes`
- If verification status is `Verified` (`id == 1` in current code), then `amount`, `bankDetail`, and `paymentType` are required
- `isReturn` defaults to `false`
- `update-payment-record` validates all item codes to start with `ORD` or `UJC`; all `ORD`/`UJC` codes must exist
- `update-payment-record` is blocked when the current verification status is `3` or `4`
- For payment type `4`, order `paidAmount` is recalculated using `isReturn` direction (`false` add, `true` deduct), including old-effect revert on update/delete
- `update-payment-verification-status-or-delete` accepts either `verificationStatusId` or `isDeleted=true` (not both)
- Deletion is allowed only when the current verification status is **not** `3` or `4`

## 6) Practical Notes for Consumers

1. **Use JWT for most operations.** Only the routes listed as public should be called without a bearer token.
2. **Send `@Valid`-friendly payloads.** Validation errors return a structured conflict/bad-request response.
3. **Prefer the `object` field for normal success payloads.** Some endpoints still use `desc` heavily for status text.
4. **POST is used for many retrieval operations.** Several list endpoints use JSON bodies instead of query parameters.
5. **SSE endpoints never return normal JSON data.** Treat them as streaming endpoints.
